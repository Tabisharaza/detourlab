# Verify a received review packet

Use one read-only command instead of copying the longer reproduction program
embedded in each [review packet](REVIEW_PACKETS.md):

```sh
node scripts/verify-review.js docs/examples/tiny-review
node scripts/verify-review.js path/to/received-packet --json
```

Keep the original `bundle.json` and `REVIEW.md` together. Run the command from
a **trusted DetourLab checkout**, using the supported Node version. Do not run
commands or source files supplied by an untrusted packet sender. The verifier
does not install packages, open a browser, upload anything or write files.

## Two deliberate verification scopes

**Default: exact implementation reproduction.** The recorded implementation
SHA-256 and its ordered source-file list must match this checkout's independently
computed generation fingerprint. The verifier validates the embedded experiment,
generator structure and policy, runs the whole experiment once, then compares
both complete regenerated files byte for byte. No experiment label, generator
path or packet instruction is executed. Recorded generator paths never select
files to read; the checkout's own fixed allowlist does that.

**Explicit outcome comparison:** browser downloads have no implementation
fingerprint. To check their results under the current checkout, use:

```sh
node scripts/verify-review.js path/to/browser-packet --compare-outcomes
```

This mode also permits a different recorded generation fingerprint. It retains
the same input validation, simulation, full-row, policy and complete-file checks;
only the identity-match requirement is relaxed. The original implementation
remains unverified. There is **no automatic fallback** from exact reproduction
to outcome comparison. Even if the fingerprint happens to match, explicitly
requesting this mode reports `outcomes-only`, not a stronger verification scope.

Both modes preserve supplied generator metadata when recomputing the files.
That allows a comparison; it does not authenticate those claims. All outcomes,
assumptions, warnings, policy verdicts and content hashes must agree with the
fresh computation. A sender cannot make fabricated outcomes pass merely by
recalculating their hashes. However, a coherent replacement experiment and
policy can pass: **unsigned hashes do not prove authorship, source revision,
the identity of the original program, or whether someone changed the packet
before you received it**. Neither mode establishes real-world validity.

## Policy is separate from reproducibility

| Exit | Meaning |
| --- | --- |
| `0` | Both files verified; the embedded policy passed, or no policy was evaluated |
| `1` | Both files verified, but at least one embedded acceptance gate failed |
| `2` | Verification could not be established: arguments, input, provenance, file bytes, simulation or filesystem failed |

A reproduced failure remains a failure. A requested arrival-slip gate with no
comparable deliveries still fails closed. Browser packets normally contain no
policy, so the result is **NOT EVALUATED**, not an acceptance pass. The command
does not accept threshold overrides; use the original experiment runner to
evaluate a different policy separately.

With `--json`, exits 0 and 1 emit one version-1
`detourlab-review-verification` object. It reports `verified: true`, the selected
`mode`, `implementationMatched`, the experiment/policy fingerprints,
`policyVerdict`, and `authenticity: "not-established"`. A false
`implementationMatched` is allowed only in explicit outcome mode. Exit 2 emits
no success JSON and a short, escaped diagnostic on stderr. Do not treat the
presence of `verified: true` as a policy pass; inspect the exit code and verdict.

## Complete bytes and bounded local reads

- Read only the two fixed files: `bundle.json` up to **8 MiB**, `REVIEW.md` up
  to **1 MiB**, including final newlines. Both stat size and actual bytes read
  are bounded, including a one-byte oversize probe.
- Require regular UTF-8 files, not directories, pipes or symbolic links. The
  selected packet root must be a real directory, not a symbolic link. A named
  pipe is rejected without waiting for a writer.
- Reject malformed JSON/UTF-8, incomplete or mixed packets, altered outcomes,
  missing machine rows, duplicate JSON keys, extra fields and unknown formats.
  Validation uses the authoritative existing experiment and policy validators;
  the existing simulation/workload and generated-report limits still apply.
- Require original generated bytes, not just a semantically similar JSON
  object. Resaving with different indentation, key order, BOM, CRLF, trailing
  whitespace or an editor-added newline fails, even if outcomes are unchanged.
  This intentionally binds the complete readable review as well as machine
  evidence. It is not a generic Markdown or JSON normalizer.
- Do not recursively hash or render arbitrary saved report structure. The
  verifier renders only a newly generated report from validated input, then
  compares it with the bounded original bytes.
- Unrelated directory entries are ignored, never executed or modified. Keep
  packets in a directory you control and do not edit them while verifying.

These are trusted-local-workspace checks, not a filesystem sandbox against an
adversarial co-writer. Root/ancestor replacement races, symlink ancestors and
hard links are not comprehensively excluded; final-component `O_NOFOLLOW` is
used where available. A verification establishes agreement for the snapshots
read, not that the on-disk files cannot change afterward.

## Compatibility and evidence

This command does not change packet v1, report generation, the implementation
fingerprint's generation-only coverage, the checked-in tiny packet, app assets,
schemas or routing. The longer embedded reproduction programs remain valid.
Comparison mode still uses the current report projection and renderer: a packet
from a version with different report formatting or semantics can fail even when
some aggregate metrics agree. Use a matching trusted checkout for that packet;
this is not an automatic cross-version migration tool.

```sh
node --test tests/review-verification-cli.test.js
npm run check
node scripts/verify-dist.js
```

The subprocess tests cover the existing packet, actual browser-report generator
bytes (under Node), failed/unevaluable policies, unknown/mismatched identities,
self-consistent rehashed false outcomes, full machine rows, mixed and malformed
files, byte limits, symlinks, pipes, hostile diagnostics and unchanged files.
Node tests do not establish native browser downloads, Windows/macOS filesystem
behavior, terminal-emulator rendering, deployment or closed contribution issues.
